# Bounded fixture brief context and preparation history

Date: 2026-10-22. Branch: `mvp-brief-fixture-context`. Parent: draft PR [#148](https://github.com/Kokfu/congenial-potato/pull/148), commit `39b9449c87827f041d10f5fd80e71d101c9b0130`.

## Implementation and evidence semantics

The worker now prepares nonempty pinned source notes for the seven explicitly reviewed fixture connection IDs. It preserves the original agent instruction and task messages, adds a fixed source-handling instruction, and supplies source JSON in a separate user message marked `external` trust. The JSON identifies policy, project, pinned revision/full-source digest, total/included character counts, truncation and the exact source prefix. Binary prefix selection accounts for JSON escaping and bounds the complete serialized source message to **6,000 Unicode characters**. It never substitutes the project's later brief. Empty and unpinned sources add no source message; other connection IDs cannot opt into this source path implicitly.

A new application table stores the exact prepared source message and its SHA-256 digest before the provider path. Generation locks the execution before authorization, checks pinned bytes/digests, validates or creates the preparation, validates price configuration, and commits before releasing locks and entering the provider path. Re-entry checks and reuses the recorded source message. Source reads validate the prepared message against the exact pin and canonical policy representation. Downgrade refuses to erase preparation history; migration does not infer historical preparations.

The source API replaces the earlier always-false `used_in_model_context` field with nullable `context` metadata. A record says **prepared**, not sent, delivered, consumed, charged or semantically followed. The saved-output view shows preparation counts, truncation and the message digest, or explicitly says no preparation was recorded. Source notes remain untrusted data, and fixture outputs remain synthetic. This does not activate native providers or real tools.

## Limits and next task

Only the source message is recorded and bounded. The entire request, reviewed memory, deadline and actual model tokenization are not pinned by this record; existing model/price validation still fails closed if the combined request exceeds its bounds. The policy is versioned in the canonical message; changed preparation policy needs an explicit compatibility decision rather than silently reinterpreting earlier records.

The preparation shares the replaceable application database and is not independent attestation, rollback protection or proof of physical durability. Quoting and trust labels do not prove general prompt-injection resistance. Receipt loss, unknown charges, actual live-provider quality, protected credentials/pricing and live activation remain separate gates. No full backend/witness/launcher suite or owner Windows Docker Desktop acceptance is claimed. Paid/live execution, product external dispatch, real effects, production connections, public deployment and merges stay disabled.

Next: a bounded structured plan contract bound to pinned source and prepared-context identity, with owner review before draft execution. Useful real-model drafting remains gated.
